# 19. 밤에 타이머가 어는가 — Core §89(예정된 깨움)를 앞두고

> **일시:** 2026-11-04 · **근거:** 이미 쌓인 soak 기록 (기기에 새로 돌린 측정이 아니다) · **결과:** 이 기록에서는 **얼지 않았다.** 다만 그동안 전원이 연결돼 있었는지는 기록이 없다
>
> [#95](https://github.com/nimwake/nimwake-android/issues/95). Core는 일정을 tokio 타이머로 돌린다 — Doze가 프로세스를 얼리면 그 타이머도 멈춘다

---

## 1. 쌓여 있던 근거

soak sampler는 Termux 프로세스의 `sleep 300`으로 돈다. proot 안 Core의 타이머와 같은 처지다 — 얼면 표본 사이가 벌어진다.

| | |
| - | - |
| 기록 | `soak-latest.csv` — Core v0.1.0, 10-15 21:07 → 10-18 04:15 (55.1h, 656 표본) |
| 표본 간격 | 평균 303s · **최대 313s** |
| 420초가 넘는 공백 | **0** |
| 밤(00–07시) 표본 간격 216개 | 최대 313s |

이틀 밤 내내 한 번도 늦지 않았다. 7초의 초과는 표본 하나를 재는 시간이다.

## 2. 이것이 말하지 않는 것

- **전원 연결 상태를 모른다.** 이 CSV에는 `plugged` 열이 없다(#73 전). `PLUGGED_USB`를 직접 본 것은 기록의 앞(10-15)과 뒤(10-22)뿐이다. battery는 76%에 여섯 시간 머문 구간(10-16 15:22–21:25)도 있고 96%에서 1%로 꾸준히 줄어든 구간도 있다 — 꽂힌 채 전류가 모자랐는지 빠져 있었는지 가릴 수 없다. Android의 Doze는 전원에 연결돼 있으면 들어가지 않으므로 이 차이가 중요하다
- 그래서 이 기록은 'Doze에서도 타이머가 돈다'의 증거가 **아니다.** '이 운영 구성에서 이틀 밤 늦지 않았다'까지만 말한다
- Core의 타이머 자체를 잰 것이 아니다 — §89가 아직 없다

## 3. 판단

| | |
| - | - |
| 운영 전제 | 서버 폰은 **충전기에 연결돼 있다.** 빠지면 10분 안에 `battery unplugged` 알림 (#73, #85) |
| wake lock | 쥔다 — 이미 부팅 때 쥐고 있었다. 추가 배터리 비용이 새로 생기지 않는다. 다만 부팅 스크립트에서만 쥐어, `make install` 직후나 손으로 시작한 서버에는 없었다 → `nimwake-host start`가 쥔다 |
| AlarmManager | **지금은 넣지 않는다.** 놓친 기록이 없다. 아래 측정에서 놓치는 수치가 나오면 다시 본다 |
| 놓친 실행 | Core가 건너뛴다(§89). 재시작이 작업 시각에 걸리면 그날 실행이 사라진다 — 배포는 작업 시각 직전을 피한다 |

## 남은 측정 — Core §89 태그가 나온 뒤

1. `[schedule]`을 쓴 앱 하나, 벽 충전기, 사흘 — 일정 수 대비 실제 실행 수와 지연
2. 충전기를 뺀 하룻밤 — Doze가 실제로 놓치는 수 (사람이 필요하다)
3. wake lock을 쥔 채 충전기를 뺀 하룻밤 — 위와의 차이

soak의 `plugged` · `battery_status` 열(#73)이 이번에는 연결 상태를 함께 남긴다.
